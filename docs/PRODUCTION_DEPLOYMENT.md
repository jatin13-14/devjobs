# Production deployment and release runbook

No hosting target, domains, credentials or infrastructure are selected or provisioned by this repository. Passing local tests does not certify a deployment. Use `DJANGO_SETTINGS_MODULE=config.settings.prod` for every production process and management command; never use `runserver` in production.

## Configuration implemented

- Explicit `DATABASE_URL` identifying PostgreSQL is mandatory; production rejects SQLite and missing URLs. Credentials come from the deployment secret manager. Select connection TLS and CA verification according to the database provider/network; use URL parameters supported by psycopg. Database connect timeout is three seconds.
- `DJANGO_SECRET_KEY`: unique random secret, at least 50 characters, no example/placeholder values. `DJANGO_DEBUG` must be false. Environment booleans accept only `true`/`false`.
- `DJANGO_ALLOWED_HOSTS`: mandatory comma-separated explicit hosts/IPs; no wildcard, scheme or ports.
- `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS`: default empty in production. Supply exact HTTPS origins, without paths, only where needed. Same-origin SPA deployments can leave them empty. CORS is not authorization.
- `DJANGO_CACHE_URL`: Redis/Rediss shared by all workers for the existing login throttle. Configure private network access, credentials/TLS and availability. Startup validates configuration; readiness checks availability. Redis socket/connect timeouts are two seconds. No new Redis infrastructure is added.
- Secure session/CSRF cookies, HttpOnly session cookies, nosniff, same-origin referrer policy and DENY framing are enabled.
- HTTPS redirect defaults true. If TLS redirects are exclusively enforced by the edge, explicitly set `DJANGO_SECURE_SSL_REDIRECT=false` and `DJANGO_HTTPS_ENFORCED_AT_EDGE=true`. Only enable `DJANGO_SECURE_PROXY_SSL_HEADER=true` with a trusted proxy that strips client scheme headers and overwrites `X-Forwarded-Proto`. Prevent direct public access to upstream workers. Otherwise keep proxy trust disabled. Sanitize forwarded IPs before configuring `DRF_NUM_PROXIES`; default zero ignores them. Decide proxy topology during deployment.
- HSTS defaults zero until HTTPS is verified. Set nonnegative `DJANGO_SECURE_HSTS_SECONDS` deliberately; include-subdomains/preload require operator review of domain coverage. Preload validation requires at least one year and include-subdomains. Run `manage.py check --deploy` with the real environment; investigate every warning (including intentional HSTS policy).

Base/dev behavior retains local defaults. Production settings must not inherit a workstation `.env`; keep that file absent from deployment images and inject environment settings securely.

## Private storage and resource controls

Local Django FileSystemStorage remains the default. Production requires an explicit absolute `PRIVATE_RESUME_ROOT` on a durable private mounted volume, outside all static/media roots, accessible to every API worker using the same DB. Restrict the service directory to 0700 and files to 0600; exclude public routing, directory indexes and untrusted writers. An absolute path alone does not prove durability; provision and test the mount before release.

Alternatively set `PRIVATE_RESUME_STORAGE_BACKEND` to an installed Django Storage subclass import path. It is instantiated with no arguments and must obtain its settings from operator-managed configuration. No cloud adapter/dependency/credentials are supplied. It must provide private save/open/delete, globally consistent UUID keys, no public URLs, bounded I/O timeouts, and exists/listdir/get_modified_time for offline cleanup. Validate permissions, concurrent writes, read-after-write and failure behavior before use. Resume download always passes through the authenticated API; do not replace it with public URLs.

`RESUME_MAX_BYTES` defaults 5242880 and must be positive. PDFs are read only up to the limit plus one byte; structure/encryption/pages are validated without rendering or text extraction. Multipart files above 1 MiB spool to temporary disk; at most one file is accepted. Configure edge body limits (file limit plus bounded multipart overhead), upload duration/rate limits, temporary-disk quotas, worker memory/CPU/time budgets, and concurrency limits. Application limits cannot prevent multipart spooling or every adversarial PDF parser resource attack. Structural validation is not malware scanning or sanitization. Downloads are attachment/no-store/nosniff/sandbox responses.

Replacement/deletion cleanup runs after DB commit. Crashes, cascading account deletions and failed deletes can leave orphans; DB and storage are not one atomic system. Retain the current document only, without application-time snapshots. Suspension retains files but revokes access; withdrawal revokes recruiter access. Already-open streams can finish. Set retention policy and reconcile after coordinated restore. `manage.py cleanup_resumes` is a count-only dry run; stop all resume writers before `--delete`. Only unreferenced UUID PDFs older than at least 24 hours are deleted. Unknown files (including failed `probe-*` readiness artifacts) require private operator reconciliation; never blindly remove files during writes.

## Probes, monitoring and operations

`GET /api/v1/health/` is dependency-free liveness. `GET /api/v1/ready/` checks `SELECT 1`, shared cache set/get/delete, and a tiny private storage write/read/delete. Returns only `{"status":"ready"}` (200) or `{"status":"unavailable"}` (503), no-store. Invalid bearer headers do not break probes; other endpoint authentication/authorization remains unchanged. It does not inspect schema migration state; migration verification is a rollout gate. Storage probes need write/delete permission and may incur storage requests. Limit probe frequency/concurrency at the edge; choose timeouts above dependency bounds and configure adapter/DB statement timeouts. Use HTTPS probes or an edge-enforced HTTPS arrangement; probes have no security redirect exemption. Monitor latency, 5xx, readiness failure, disk space, DB/cache saturation, upload failures and generic cleanup warnings. Redact authorization headers, cookies, URLs with credentials, request bodies, applicant data and storage keys in logs. Define alert routing with actual operators during deployment.

## Rollout and rollback

1. Choose process runner, TLS/proxy topology, PostgreSQL/Redis services, durable private storage, secret management, domains/origins and operational owners. Restrict DB/cache/storage access. No choices are implied here.
2. Back up PostgreSQL and private files as a coordinated pair, encrypt and access-control backups, define retention/RPO/RTO, and rehearse restoring both to an isolated environment. Never use test databases as production.
3. Install reviewed backend requirements and frontend lockfile dependencies. Build frontend with the actual public `VITE_API_BASE_URL` (no secrets in VITE variables). Run the release checks in PROJECT_STATUS.md and production `check --deploy` in staging.
4. Inspect `manage.py showmigrations` and `manage.py migrate --plan` on the intended DB. Apply `manage.py migrate --noinput` once using the release operator, before new workers serve traffic. Existing outstanding migrations include resume metadata, company/job moderation flags, immutable moderation audit triggers and integrity constraints; preflights may reject inconsistent historical data. Resolve through reviewed migrations, never ad hoc data resets. Test migration execution and rollback feasibility on a restored staging copy first.
5. Run `manage.py collectstatic --noinput`; serve STATIC_ROOT separately through the selected web server/static host, never private storage. Serve frontend `dist` with SPA fallback for frontend routes only; API/admin failures must not become SPA HTML. Use a production WSGI/ASGI runner with bounded worker resources, graceful drain, upstream timeouts and trusted networking.
6. Validate readiness, actual TLS/headers, origins, static assets, authenticated resume denial across roles/companies, registration/application/moderation journeys and backups in staging. Provision admin through trusted `createsuperuser` operations, no default credentials. Release only after these deployment gates pass.
7. Keep previous app/static artifacts and compatible configuration. On failure drain traffic and restore the prior app only if schema-compatible. Avoid reversing audit/integrity migrations casually; use a reviewed forward fix or coordinated DB/private-storage restore during maintenance. Verify readiness and access revocation after recovery. Secret rotation can invalidate JWTs/sessions and needs an explicit operational plan.

These are deployment requirements, not evidence of performed deployment, backup restoration, edge configuration or staging validation.
